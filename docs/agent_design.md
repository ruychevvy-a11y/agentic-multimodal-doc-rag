在「检索 → 查看前 4 页页图 → 一次作答」的基线之上，为模型提供三个工具，使其在证据不足时自行补充检索与翻页，并最终给出答案与引用页。

## 设计动机

检索能把全部金标页都排进前 4 的题目占 73.1%。其余题目中，基线在证据不完整的情况下只能强行作答：在留出的 200 题上，起点证据不全的题 Acc 仅 0.296，跨页题 0.451，而证据齐全的题为 0.699。

固定增加页数并不划算：k=6 相对 k=4 总分仅 +0.015（不显著），增益全部集中在证据不全的题（+0.134\*），不可回答题反而更容易强行作答，成本还增加 30%。因此需要的是按需投入——简单题一次作答即结束，只有确实缺证据的题才触发检索。

## 结构

```
起点：system 指令 + user（问题 + 检索得到的前 4 页页图，每页带 [Page N] 标签）
  │
  ├─ 循环，最多 5 次模型调用：
  │    模型返回 tool_calls？
  │      search_pages(query)      --> 在本文档内检索 --> 返回前 5 页的「页号 + 查询相关摘要」（纯文字）
  │      view_pages(page_numbers) --> 校验页号、跳过已看过的页、每次最多 4 页
  │                                   --> tool 消息返回文字，页图放在紧随其后的一条 user 消息中
  │      answer(answer, cited_pages) --> 记录答案与引用页，结束
  │    未返回 tool_calls --> 正文即为答案，结束
  │
  └─ 用尽 5 次调用或单次调用超时 --> 兜底：以 tool_choice="none" 再调用一次，
                                      要求仅依据已看过的页作答（允许答 Not answerable）
```

每一步都产出一条结构化的步骤记录，包括模型调用、工具调用与最终答案：评测据此统计过程指标，demo 直接将其推送到前端展示。

## 三个工具

| 工具 | 参数 | 返回 | 设计理由 |
|---|---|---|---|
| `search_pages` | `query` | 前 5 页的页号与一行查询相关摘要，已看过的页会标注 | 仅返回文字，成本低。模型据此判断哪些页值得查看，再决定是否加载页图 |
| `view_pages` | `page_numbers` | 文字确认 + 页图 | 接受任意页号，不限于检索结果：表格标注「续下页」时可查看下一页，目录标明某节在第 45 页时可直接跳转 |
| `answer` | `answer`, `cited_pages` | 结束本题 | 只有调用该工具才算结束，停止条件明确；引用页为结构化输出，可直接用于证据核对 |

摘要取「查询相关」的窗口而非正文开头：页面正文的开头多为上一页的续句或页眉，例如 10-K 的每一页都以 "Table of Contents" 开头，对选页没有帮助。

## 上限与兜底

| 参数 | 值 | 依据 |
|---|---|---|
| 单题模型调用次数 | 5 | 限制最坏情况下的成本；实测平均仅 1.59 次 |
| 每次 `view_pages` 页数 | 4 | 一张页图约 2500 token，且每轮都会重发历史 |
| 单题累计查看页数 | 12 | 在前 4 页之外仍缺金标页的题中，缺 1 页的占 21.8%、缺 5 页以上的不足 3%，12 页可覆盖 99.4% |
| 搜索返回条数 | 5 | 闭域重排 recall@5 为 0.796、@10 为 0.871，前 5 条已占前 10 命中的九成 |
| 单次调用超时 | 45 s | 超时不重试，直接进入兜底，避免单题阻塞数分钟 |
| 思考预算 | 1024 token | 与默认思考准确率打平，p90 由 68 s 降至 15.6 s |

异常一律不抛出，而是以文字形式返回给模型，由其自行修正：参数不是合法 JSON、工具名不存在、页号越界、重复检索同一查询（直接返回上次结果，不再调用检索）、重复查看同一页（提示该页已在上文中）。内容审核拦截与限流沿用统一的重试退避策略。

## 取舍

| 决定 | 选择 | 理由 |
|---|---|---|
| 起点 | 先给出基线的前 4 页，工具用于补充 | 简单题一次调用即结束，成本约等于基线；若只给问题、完全依赖 agent 自行检索，简单题也需多轮 |
| agent 数量 | 单 agent | 单文档问答不存在需要分工的子任务，多 agent 只会带来成倍的调用开销与冲突处理 |
| 调用方式 | function calling | 模型原生返回结构化的 tool_calls，无需自行编写 `Action:` 解析器 |
| 结束方式 | 必须调用 `answer` | 停止条件明确，引用页为结构化输出 |
| 记忆 | 仅保留单题内的对话轨迹 | 每题相互独立，没有可复用的跨题信息 |
| 框架 | 自行实现循环，约 100 行 | 需要逐步记录 token、耗时与工具失败，需要控制上限与兜底，且需与基线共用同一套判分 |
| MCP | 不使用 | 工具运行在同一进程内、只有一个调用方，而 MCP 解决的是多方接入问题 |

## 实现要点

- **tool 消息中不能携带图片**：接口会返回 400，页图必须放在 tool 消息之后紧随的一条 user 消息中。
- **检索器可在多线程间共用**：同一个检索器在 12 个线程上处理 240 题，候选结果与串行执行逐位一致，因此评测可以并发、demo 可以在工作线程中调用检索。

## 效果

在留出的 200 题上与一次作答配对比较（同一套检索）：

| 路线 | 全部 | 跨页题 | 起点证据不全 | 不可回答题 |
|---|---|---|---|---|
| 一次作答 | 0.645 | 0.451 | 0.296 | 0.805 |
| agent | 0.655 | 0.556 | 0.424 | 0.707 |

总分打平，增益集中在跨页题与证据不全的题，代价是不可回答题上更容易强行作答。200 题中仅 28% 触发检索，兜底强制作答 1 题，工具零报错，每题成本 ¥0.0234，同批题目上一次作答为 ¥0.0111。

此外评估过两种增强方法：其一是作答后由模型核验证据，判定不支持则改为拒答；其二是在核验未通过时允许 agent 再补充检索一轮。前者总分打平、未达到事先设定的判据，后者在合并 400 题上 +0.026\*，但每题成本升至 ¥0.032、p90 达 54 s。两者均未采用。完整数字见 [results_summary.md](results_summary.md)。
